11// Given, GfxRender onward: scene-object creation/manipulation, material
12// editing, and scene lighting. CreateObjectPanel/ObjectModePanel
13// (spawning and picking/manipulating scene objects) stay iModel (5)/
14// Ray (6)-only in practice -- Camera & Shading (4)/Shapes (3) have no
15// scene-object manipulation of their own -- but live here alongside
16// MaterialPanel/LightsPanel/BackgroundColorPanel (which those two *do*
17// use) rather than in a separate file, since none of these panels has
18// any dependency of its own that would force a split. Self-contained,
19// like every other panel in this codebase -- Draw() touches only this
20// file's own classes' members. Each assignment's own app code (the one
21// place that knows both its own scene representation's shape and
22// whichever given types like SceneMaterialDesc/Light it converts to/
23// from) reads these accessors and acts on them itself -- unlike
24// CameraParametersPanel's own sync glue (see camera_gui_sync.h), there's
25// no cross-assignment-identical conversion here to promote into a shared
26// library, since each assignment's own scene representation is student-
27// designed, not an instructor-fixed shape.

63// Owns the *current* material values (ambient/diffuse/specular/
64// specular exponent/texture/shader style, plus the Material File path
65// used to load and save them) shown and edited in the panel -- a plain
66// value holder, no behavior of its own, and completely decoupled from
67// whatever object (if any) is currently selected: editing these fields
68// never touches any object directly, and selecting an object never
69// overwrites these fields either. Apply/Get are the *only* bridge to a
70// selected object, each a one-shot "clicked this frame" flag; ImodelApp's
71// own code (which alone knows its scene object's shape) does
72// `selected_object->material = material_panel_.CurrentMaterial()` (or
73// the reverse) when it sees one set -- a paint-bucket/eyedropper
74// pattern, and deliberately the *only* two ways this panel and an
75// object's own material ever affect one another, so editing the panel's
76// fields or selecting a different object never silently changes the
77// other. material_path_/load_material_requested_ (and
78// material_save_path_/save_material_requested_, its own mirror image for
79// writing) live under the same toolbar dropdown as the reflectance
80// fields below, since loading/saving a file and reviewing/editing/
81// applying what it loaded is one continuous task, not unrelated ones
82// split across separate buttons. ImodelApp parses the named .mtl file
83// (via GfxRender's Material, the same class ImodelApp::LoadSceneFile()
84// already uses for a bare .obj's own adjacent .mtl) and writes the
85// result back into this panel's own ambient_/diffuse_/specular_/
86// specular_exponent_/texture_ fields on Load, and the reverse -- these
87// same fields, hand-written as a Wavefront .mtl (GfxRender's own
88// Material class only loads, it has no writer) -- on Save; the same
89// "load populates the panel, Apply/Get moves it to/from an object"
90// two-step Camera & Shading (4) uses, plus this one extra "Save writes
91// the panel back out to disk" leg. shader_style_ is conceptually part of
92// a material (it's a field of scene_io.h's own SceneMaterialDesc,
93// alongside the reflectance values), so it belongs in the same panel and
94// moves to/from an object through the same Apply/Get pair, not a
95// separate whole-scene setting.

135 // DrawFloatingWindow() below open/closed, highlighted (the same way
136 // a selected radio-button tool is) whenever that window is currently

145 // Draws Draw()'s own content (see its own show_shader_style/
146 // show_apply_get_buttons params, threaded straight through here)
147 // inside a real, independent, movable ImGui window (via
148 // ToggleWindowPanelBase::DrawToggleWindow()) rather than a transient

231// Left-mouse interaction mode -- Select plus the three manipulation
232// verbs. No Apply Material/Eyedropper click modes here -- selecting an
233// object never auto-populates MaterialPanel's fields (editing/selection
234// are decoupled, see MaterialPanel above), so applying/getting a
235// material goes through MaterialPanel's own explicit Apply/Get buttons
236// instead of a dedicated picking mode. Drawn as a
237// Unity-toolbar/Photoshop-tool-palette-style row of square icon buttons
238// in the manipulate toolbar, exactly one highlighted at a time. Every
239// mode already selects whatever's clicked, or deselects on a click that
240// hits nothing (see ImodelApp::OnLeftMouseDown()) -- kSelect is the same
241// as the other three on mouse-down, but its own OnLeftMouseDrag() case
242// does nothing, so it's the one to reach for when
243// all that's wanted is picking (or clicking empty space to deselect)
244// without risking an accidental nudge/rotate/scale from a drag that
245// moves a pixel or two along the way. kRotate/kScale each read the X/Y/Z
246// keys during a drag to constrain it to a single axis (instead of the
247// free trackball rotate/uniform scale a plain drag does), and Ctrl on
248// top of one of those to pick WORLD instead of the object's own LOCAL
249// axes -- see each one's own tooltip (Draw()'s own kTooltips) for the
250// exact key combinations, and ImodelApp::OnLeftMouseDrag()'s own switch
251// for how each is implemented.
252class ObjectModePanel {
253 public:
254 enum Mode { kSelect = 0, kTranslate, kRotate, kScale };
255
256 void Draw();
257
258 Mode selected() const { return mode_; }
259 // Overwrites which tool button reads as selected -- used the same
260 // way ScenePanel::SetScenePath()/LightPanel::SetLightType() are:
261 // ImodelApp's own --object-mode N (see its own ParseCommandLineArg())
262 // forces a specific tool for headless verification, the same way
263 // Camera & Shading (4)'s --shading-style/--light-type do, without
264 // needing an actual mouse click to get there.
265 void SetMode(Mode mode) { mode_ = mode; }
266
267 private:
268 Mode mode_ = kTranslate;
269};

271// One scene light's own editable fields -- position (point) or
272// direction (directional), plus Ia/Id/Is (ambient/diffuse/specular
273// *intensity*, matching Camera & Shading (4)'s own LightPanel naming
274// convention). Plain data, no behavior -- LightsPanel owns a
275// std::vector of these; ImodelApp converts each one to a GfxRender
276// Light (scene_io.h) when it actually renders or saves the scene.
277struct SceneLightEntry {
278 enum Type { kPoint = 0, kDirectional };
279 Type type = kPoint;
280 // Close to the origin (rather than PointLight's own far-away
281 // default) so it's actually visible from every assignment's own
282 // default camera position -- iModel (5)/Ray (6) overwrite this on
283 // every scene load anyway (see SetLights()), but Camera & Shading
284 // (4) never loads a scene at all, so this struct's own default is
285 // the *only* light it ever has.
286 float position[3] = {0.6f, 0.35f, 0.8f};
287 float direction[3] = {-1.0f, -1.0f, -1.0f};
288 float ia[3] = {0.15f, 0.15f, 0.15f};
289 // Full intensity (unlike ia's own dim ambient default) -- easier to
290 // debug shading against: any surface a diffuse/specular term should
291 // reach reads unambiguously lit rather than needing to be
292 // interpreted against a partial intensity.
293 float id[3] = {1.0f, 1.0f, 1.0f};
294 float is[3] = {1.0f, 1.0f, 1.0f};
295 // Draws this one light's own debug indicator (a small dot at its
296 // position if kPoint, a long line along its direction if
297 // kDirectional -- the same yellow marker/arrow Shapes (3) and Camera
298 // & Shading (4) each drew for their own single light, via GfxRender's
299 // own DebugGfx -- see ImodelApp::DrawLightIndicators()) when true.
300 // Defaults on, matching those two assignments' own always-on
301 // behavior; this is the first one where it's actually optional, since
302 // several lights' own markers at once can clutter a busy scene more
303 // than a single one ever did.
304 bool show_debug = true;
305};

307// The scene's own light list -- add/remove lights, each with its own
308// sub-section (see Draw()), rather than Camera & Shading (4)'s single
309// editable light with an "override the whole scene's lights" flag:
310// iModel (5) always renders every light in this list (see ImodelApp::
311// DrawUsingOpenGL()'s own multi-pass loop), with no separate "scene's
312// own lights vs. this panel's light" distinction to arbitrate, since
313// this panel *is* the scene's own light list. Starts with one default
314// light (SceneLightEntry's own default, above) so a freshly launched
315// app -- or a freshly loaded scene with no lights of its own -- still
316// has something to see by; Draw() refuses to remove the last remaining
317// light for the same reason. Uses the same DrawToolbarButton()/
318// DrawFloatingWindow() toggle pattern as MaterialPanel/
319// CameraParametersPanel/RaytracePanel -- a real window, not a transient
320// dropdown popup, since with several lights each carrying several
321// fields, the panel gets tall enough that leaving it open while working
322// elsewhere in the 3D view (e.g. dragging a light's own debug marker, or
323// comparing a change against the rest of the scene) matters here just
324// as much as it does for MaterialPanel.
325class LightsPanel : private ToggleWindowPanelBase {
326 public:
327 // Content only, no window of its own -- called by DrawFloatingWindow()
328 // below.
329 void Draw();
330
331 // A single toolbar button (see tool_button.h) that toggles
332 // DrawFloatingWindow() below open/closed, highlighted whenever that
333 // window is currently open. force_open forces the window open (for
334 // headless verification -- see ImodelApp::ParseCommandLineArg()'s
335 // own --open-popup lights).
336 void DrawToolbarButton(bool force_open = false);
337
338 // Draws Draw()'s own content inside a real, independent, movable
339 // ImGui window if the window is currently open (a no-op otherwise),
340 // rather than a transient dropdown popup.
341 void DrawFloatingWindow();
342
343 const std::vector<SceneLightEntry> &lights() const { return lights_; }
344 // Replaces the entire light list -- used when loading a scene file
345 // whose own lights should become the editable set. Falls back to
346 // the usual single default light if given an empty list (e.g. a
347 // scene file that specifies none), for the same reason
348 // DrawToolbarButton() never lets the list go fully empty.
349 void SetLights(const std::vector<SceneLightEntry> &lights);
350
351 private:
352 std::vector<SceneLightEntry> lights_ = {SceneLightEntry()};
353};
