Detailed Description

This is the main application base class for the GfxCore Toolkit.

Create a Subclass:

To create your own graphics application, you should create a subclass of GraphicsApp and then override some key functions:

  1. User Input: To get input from the keyboard and mouse, override OnMouseMove() and/or the other On...() functions.
  2. Drawing Graphics: To draw graphics override one or more of the Draw*() functions.
    • DrawUsingOpenGL() is the right place to make 2D or 3D drawing calls using OpenGL. This includes drawing using the Mesh, GouraudShader, ShaderProgram, and all other GfxCore classes since these are all based on OpenGL.
    • DrawGUI() is the right place to make ImGui calls (ImGui::Begin(), ImGui::SliderFloat(), etc.) to draw a 2D immediate-mode user interface on top of your 3D scene.
    • InitGUI() is the right place to do any one-time ImGui setup, such as loading custom fonts.
    • InitOpenGL() is the right place to load textures, meshes, shaders, and other graphics objects that can only be created after the OpenGL context exists.
  3. Physics, Animation, AI, etc.: Override the UpdateSimulation() function to do other non-graphics calculations required by your program. This is called automatically once per frame.

Keep in mind that internally the app uses a rendering loop that looks something like this:

InitGUI(); // your hook for any one-time ImGui setup
InitOpenGL(); // your hook for initializing OpenGL graphics
while (!program_ready_to_close) {
// user input
internal_get_input_events_from_operating_system();
OnMouseMove(); // your hook for processing input
On*(); // all other event callbacks -- your hook for processing input
// phyics, etc.
UpdateSimulation(); // your hook for physics, animation, AI, etc.
// draw graphics
internal_begin_imgui_frame();
DrawUsingOpenGL(); // your hook for 2D/3D rendering with OpenGL
DrawGUI(); // your hook for drawing an ImGui-based 2D user interface
internal_render_imgui_frame();
}

A Complete Example with GUI Widgets

If you wish to add some buttons, sliders, etc. in your application, you can do this with immediate-mode calls into the Dear ImGui library from inside DrawGUI(). Unlike a retained-mode GUI toolkit, there is no separate window/widget object to construct ahead of time – you just call ImGui functions every frame to describe the GUI you want, and ImGui figures out the rest:

// This example also draws a Mesh with GouraudShader, so it links GfxMath
// and GfxRender in addition to GfxCore -- GraphicsApp itself (declared
// in this header) has no dependency on either.
#include <gfxcore.h>
#include <gfxrender.h>
class MyApp : public GraphicsApp {
public:
MyApp() : GraphicsApp(1024,768, "My Amazing App"), paused_(false) {
}
virtual ~MyApp() {}
void InitOpenGL() {
glClearColor(0.0, 0.0, 0.0, 1);
cube_.LoadFromOBJ(RenderPlatform::FindGfxRenderDataFile("cube.obj"));
shader_.Init();
}
void DrawGUI() {
ImGui::Begin("My GUI Panel");
if (ImGui::Button("Pause")) {
paused_ = !paused_;
std::cout << "Pause pressed." << std::endl;
}
ImGui::End();
}
// this callback is built into the base GraphicsApp class
void OnMouseMove(float x, float y, float dx, float dy) {
std::cout << "Mouse moved to (" << x << ", " << y << ")" << std::endl;
}
void DrawUsingOpenGL() {
Matrix4 model = Matrix4::Translation(Vector3(-1,0,0)) * Matrix4::Scale(Vector3(0.5, 0.5, 0.5));
Matrix4 view = Matrix4::LookAt(Point3(0,0,3), Point3(0,0,0), Vector3(0,1,0));
Matrix4 proj = Matrix4::Perspective(60.0, aspect_ratio(), 0.1, 10.0);
shader_.Draw(model, view, proj, &cube_, MaterialProperties(), light_);
}
private:
Mesh cube_;
GouraudShader shader_;
PointLight light_;
bool paused_;
};
int main(int argc, const char *argv[]) {
MyApp app;
app.Run();
return 0;
}

◆ InitGraphicsContext() [1/2]

virtual void GraphicsApp::InitGraphicsContext ( )
virtual

Users cannot make any graphics calls (e.g., setting the clear color, saving mesh data to the GPU) until the graphics context is initialized by calling this method.

Normally, it is called automatically by the Run() method, which then proceeds to call the InitGUI() and InitOpenGL() methods. Occasionally it is useful to have more control over the when exactly the graphics context is initiated, so it is also possible to call this method manually before Run(). In that case, Run() will recognize the context has already be initialized and will not call this method again.

After creating a new GraphicsApp, call this to start the app's mainloop.

Each time through the mainloop the app will: 1. respond any user input events by calling the On*() callback methods, 2. call UpdateSimulation(), and 3. call the two Draw*() methods. Note that Run() does not return until the user closes the app and the program is ready to shutdown.

◆ Run() [2/2]

virtual void GraphicsApp::Run ( int argc,
char ** argv )
virtual

Standard command-line entry point – every GfxCore-based assignment's main() should just be:

int main(int argc, char **argv) {
MyApp app;
app.Run(argc, argv);
return 0;
}

so that every assignment, regardless of what it's about, supports the same flags out of the box (this is what CI/grading scripts rely on):

  • --headless <output.png>: render off-screen (no window shown) via RunHeadless(), instead of running interactively, then exit with a status code reflecting success/failure. One or more frames are captured (see the three flags below) and written next to <output.png> with the frame number spliced into the filename, e.g. <output.png> of out.png produces out_000010.png for frame 10 – never a literal out.png, even when only one frame is captured, so a grading script never has to guess which naming convention a given run used.
  • --start-frame N (default 0): the first simulated frame to capture. Frames before this are still simulated (so animation/ physics state is correct by the time capturing begins), just not written out.
  • --frame-increment N (default 1): spacing between captured frame numbers, e.g. --start-frame 10 --frame-increment 5 --num-frames 3 captures frames 10, 15, and 20.
  • --num-frames N (default 1): total number of frames to capture. All three of these are ignored outside --headless mode.
  • --headless-gui: by default, --headless mode skips DrawGUI() entirely, so captured frames show only the 3D scene – no ImGui widgets, since their layout/content would otherwise vary between runs and get in the way of pixel-comparing against a reference image. Pass this flag to call DrawGUI() and composite it into the capture anyway, for the rare assignment where the GUI itself is part of what's being graded.
  • --width W, --height H: override the window/framebuffer size from the command line, e.g. so a grading script can request a consistent resolution across every submission without touching source code.
  • --help/-h: print usage (see PrintUsage()) and exit.

If none of these are given, this just calls the normal interactive Run(). An assignment that needs its own additional flags (e.g. Ray taking a --scene <file>) should override ParseCommandLineArg() and PrintUsage() rather than reimplementing argument parsing – that way the standard flags above keep working identically everywhere.

◆ RunHeadless()

virtual bool GraphicsApp::RunHeadless ( const std::string & output_path,
int start_frame = 0,
int frame_increment = 1,
int num_frames = 1,
bool include_gui = false )
virtual

Renders without ever presenting a window (the GLFW window is created hidden), simulating frames 0, 1, 2, ... and writing out the ones at start_frame, start_frame + frame_increment, start_frame + 2*frame_increment, ... up to num_frames total captures.

Each is written next to output_path with the frame number spliced into the filename (see BuildFrameOutputPath()) – never literally output_path itself, so single- and multi-frame runs always name their files the same way. Otherwise follows the same lifecycle as Run(): InitGraphicsContext(), InitGUI(), InitOpenGL(), then UpdateSimulation()/DrawUsingOpenGL() once per simulated frame. DrawGUI() is only called (and composited into the capture) when include_gui is true – false by default, since ImGui widgets would otherwise vary between runs and get in the way of pixel-comparing captures against a reference image. Returns true if every capture succeeded. You can call this directly instead of Run(int, char**) if you want headless rendering without any command-line parsing.

Sets the OpenGL clear color used to paint the background behind everything else – wraps glClearColor() and remembers the value (see background_color()) so an app that needs the background as actual data, not just a one-way GL side effect, can read back the same color its rasterized preview uses instead of keeping a second, separately hardcoded copy in sync by hand (e.g. a ray tracer shading rays that hit nothing, or a scene file format that wants to save/restore its own background). ◆ SetContentViewportTopInset()

void GraphicsApp::SetContentViewportTopInset ( float pixels)

Reserves this many screen pixels along the top of the window for a pinned toolbar/HUD strip that ImGui draws over the 2D/3D scene. Once set, the shared Run()/ RunHeadless() loop restricts the OpenGL viewport for DrawUsingOpenGL() to exactly the drawable region below that inset (see content_width()/content_height()), rather than rendering the full window and then simply letting the toolbar's own opaque pixels hide whatever was drawn underneath – most concretely useful for Ray (6)'s own per-pixel raytracing, where that hidden strip is real, avoidable work, not just a wasted rasterization pass. Zero by default (nothing reserved, the full window is drawable), matching any assignment that never calls this.

Meant to be called every frame from DrawGUI(), right alongside wherever a toolbar's own height is already computed for its own layout – harmless to pass the same value every frame (nothing about a toolbar's own height should actually change frame to frame in practice); the one-frame lag before a freshly-changed value first takes effect (this frame's own DrawUsingOpenGL() already ran against whatever the previous value was) is likewise harmless for something this static.

An assignment that already manages its own OpenGL viewport every frame (e.g. to letterbox/pillarbox a camera's own aspect ratio within the window) will find its own later glViewport() call simply overrides whatever this reserved – correctly composing the two (so a letterboxed scene also excludes the toolbar strip) requires that assignment's own viewport code to build its own rectangle from content_width()/content_height() rather than window_width()/window_height(), not just calling this alone.
